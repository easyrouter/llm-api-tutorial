# Codex 接入引导工具 — 需求澄清与开发方案（草案 v0.1）

> 承接需求：IT 部门反馈《通过 CC Switch 统一供应商配置 Codex》纯文本指南使用困难，希望开发一款轻量的、带交互界面的程序，兼具**安装向导**与**帮助文档**功能，覆盖环境检查、安装与配置引导。
>
> 本文档目的：在正式立项前澄清需求边界、给出技术管线建议，形成可评审的开发方案框架。

---

## 一、对现状的分析：问题到底出在哪

在提出解决方案前，需要先与 IT 确认对问题的诊断是否一致。通读现有指南后，有一个重要事实：**CC Switch 本身已经是图形界面工具**，并且已内置了指南中的大部分能力——环境检查（设置 > 关于 > 本地环境检查）、Codex 一键安装、供应商配置表单、环境变量冲突检测与清理。

因此"用户对纯文本指南感到困扰"更可能的根因是：

1. **流程编排缺失**：完整流程横跨 Node.js 官网、CC Switch、终端三个场景，共 7 个步骤，任何一步的前置条件不满足（如未重启终端）都会导致后续失败，而用户不知道自己卡在哪一步。
2. **分支判断前置**：用户在开始前就要回答"网关是否支持 Responses 协议"这种超出普通用户认知的问题（决定走统一供应商还是方案 F）。
3. **验证反馈缺失**：指南依赖用户自行判断"是否成功"（看版本号、看卡片颜色、发测试消息），出错时需要自己在故障诊断 A–G 中对号入座。
4. **信息冗余**：指南同时服务"公司标准场景"和"通用场景"，但公司内网关地址、模型名、协议支持情况很可能是统一的，大量字段本不需要用户理解和填写。

**结论**：新工具的价值不是"把文字变成界面"（CC Switch 已经做了），而是**把跨工具的流程串成一条有状态检测、有分支收敛、有自动验证的单一路径**，并把公司标准配置预置进去。这一诊断需要 IT 确认。

## 二、核心定位问题（澄清优先级最高）

新工具与 CC Switch 的关系存在三种可能定位，选择不同，工作量、风险和技术方案完全不同：

### 定位 A：引导编排层（Companion / Onboarding Assistant）

工具负责环境检测、自动下载安装 Node.js / CC Switch / Codex、每步完成后自动验证，但**配置环节仍引导用户在 CC Switch 界面中操作**（配图 + 分步高亮说明 + 完成检测）。

- 优点：不触碰任何配置文件，与 CC Switch 无状态冲突；CC Switch 升级时只需更新截图和文案。
- 缺点：配置环节仍需用户手动填表，体验提升有限；CC Switch 界面迭代快（指南自己也注明"以应用内实际显示为准"），截图维护有长期成本。

### 定位 B：全自动配置器（绕过 CC Switch）

工具直接生成 `~/.codex/auth.json` 与 `~/.codex/config.toml`（指南"参考"章节已给出完整格式），用户只需粘贴 API Key，一键完成。CC Switch 变为可选项。

- 优点：路径最短，用户操作最少；如果公司场景是"单一网关 + 仅 Codex"，CC Switch 这个中间层本身可能就是多余的（指南选型参考表也承认：仅用 Codex 时应用专属供应商路径更短）。
- 缺点：与 CC Switch 状态冲突——若用户之后又装了 CC Switch，双方都写同一份 config.toml，互相覆盖；Codex 配置格式属于上游内部约定，随版本变化的风险由我们承担；方案 F（Chat Completions 协议转换）依赖 CC Switch 的本地代理，无法绕过。

### 定位 C：混合（推荐作为讨论起点）

环境检查与安装环节全自动（定位 A 的能力），配置环节视公司标准而定：

- 若公司统一使用支持 Responses 协议的网关 → 工具预置 Base URL 与模型名，用户只粘贴 Key，直接写 Codex 配置文件（定位 B 路径），CC Switch 可不装；
- 若存在需要协议转换或多供应商切换的用户群 → 引导安装 CC Switch 并进入定位 A 的引导路径。

### 需要 IT 回答的定位类问题

| # | 问题 | 影响 | 结论 |
|---|------|------|---|
| 1 | 公司内网关地址、模型名称、Reasoning Effort 是否全员统一？是否可以硬编码/由配置中心下发？ | 决定用户需要填几个字段（最好只剩 API Key） | 只有网关地址不变 |
| 2 | 公司网关是否确定支持 Responses 协议？是否存在必须走方案 F（Chat Completions）的用户？ | 决定能否绕过 CC Switch、是否需要保留分支流程 | 支持并且推荐使用 Responses |
| 3 | 用户是否有"多供应商切换"的真实需求，还是一次配好长期不动？ | 决定 CC Switch 是必装项还是可选项 | 需要多供应商切换 |
| 4 | 是否允许工具直接写入用户目录下的 `~/.codex/` 配置文件？ | 定位 B/C 的合规前提 | 否 |
| 5 | 除 Codex 外，Claude Code / Gemini CLI 是否也在本次范围内？ | 统一供应商功能是否还有意义 | 需要配置Claude Code和Codex cli |

## 四、功能需求初稿（模块分解）

以下按定位 C 的假设列出，定位确认后裁剪。

### M1 环境检查（进入向导即自动执行，实时刷新）

- 操作系统与架构识别，比对最低版本要求（Win10 x64 / macOS 12 / Ubuntu 22.04 等）
- Node.js：是否存在、版本是否 ≥ 18、npm 是否可用
- Codex：`codex --version` 是否可执行；不可执行时区分"未安装"与"PATH 未生效"（对应故障 E）
- CC Switch：是否已安装（按定位决定是否检查）
- 环境变量冲突：检测 `OPENAI_API_KEY` 等变量（对应故障 D），标注来源
- 网络连通性：npm registry / 网关地址可达性预检
- 每一项给出 通过 / 警告 / 阻断 三态，阻断项附带"一键修复"或跳转说明

### M2 安装引导

- Node.js：优先引导下载 LTS 安装包（或内网镜像地址），安装后自动复检；macOS 检测到 Homebrew 时提供 brew 路径
- Codex：一键执行 `npm install -g @openai/codex`，网络慢时自动切换镜像源；显示实时进度与日志
- CC Switch（若在范围内）：从官方渠道下载并校验哈希，覆盖指南中的防伪警告
- 所有安装动作前明示将执行的命令，用户确认后执行（合规问题 #7/#17 的答案决定确认粒度）

### M3 配置向导

- 公司标准场景：预置 Base URL 与模型名（问题 #1 的答案），用户仅粘贴 API Key；实时校验 Key 格式（`sk-` 前缀、无空格换行——对应故障 A 的第一诱因）
- URL 处理规则可视化：按指南"API 地址的处理规则"实时预览最终生效地址（对应故障 B）
- 协议分支：若须保留方案 F 场景，在此处以一个问题收敛分支，而不是让用户通读文档自行判断
- 写入配置（定位 B/C）或引导 CC Switch 操作（定位 A），完成后展示将写入/已写入的配置摘要

### M4 生效与验证

- 明确提示"完全关闭终端窗口"（对应故障 C，指南称其为最常见问题），Windows 下可检测并列出仍在运行的终端进程
- 一键验证：后台以新会话执行 `codex --version` + 向网关发起最小测试请求，直接告知成功/失败
- 失败时自动进入 M5 诊断，而非展示错误码让用户自查

### M5 自动诊断（对应故障 A–G）

- 将指南故障表转译为规则引擎：401/403 → Key 三项检查清单；404 → URL 规则复检；无变化 → 终端重启检测；命令不存在 → PATH/Node 检查链
- 每条诊断结论附带一键修复或精确操作指引
- 无法自动解决时，一键生成脱敏诊断报告（环境信息 + 错误信息 + 脱敏后的配置），替代指南末尾"提交反馈时请附截图"的人工流程

### M6 帮助文档

- 内嵌指南全文的结构化版本，支持搜索
- 与向导联动：每个向导步骤提供"了解更多"跳转到对应章节；文档中的操作项提供"去执行"跳回向导
- 内容来源与更新机制按问题 #18 的答案确定

## 五、技术管线选型

### 5.1 约束条件回顾

- 需求方明确要求"轻量"
- 必须能执行本地系统操作：跑命令（node/npm/codex）、读写用户目录文件、读环境变量、检测进程——**纯网页方案出局**（浏览器无法做本地检查），除非配一个本地 agent，复杂度反而更高
- 目标平台待确认（问题 #6），是最大的选型变量

### 5.2 候选方案对比

| 方案 | 跨平台 | 产物体积 | 内存占用 | 开发效率 | 团队技能要求 | 备注 |
|------|--------|----------|----------|----------|--------------|------|
| **Tauri 2**（Rust + Web 前端） | ✅ 三平台 | 约 5–15 MB | 低 | 中 | 前端 + 少量 Rust | CC Switch 本身即基于 Tauri 2 构建，生态验证充分；系统操作经 Rust 侧命令暴露，安全模型好 |
| **Wails v2/v3**（Go + Web 前端） | ✅ 三平台 | 约 10–20 MB | 低 | 中高 | 前端 + Go | Go 比 Rust 上手快，做进程调用/文件操作代码量小；社区小于 Tauri |
| **Electron** | ✅ 三平台 | 100 MB+ | 高 | 高 | 纯 JS/TS | 开发最快，但与"轻量"要求直接冲突；作为"帮用户装 Node 的工具"自带一个 Chromium 观感欠佳 |
| **.NET WPF / WinUI 3** | ❌ 仅 Windows | 依赖运行时或自包含约 60 MB | 中 | 高（若团队有 C# 经验） | C# | 若答案是"Windows-only 机队"，这是最省事、最易被企业 IT 管控（MSI + 组策略分发）的路线 |
| **命令行 TUI 向导**（Node/Go） | ✅ | 极小 | 极低 | 最高 | 任意 | 成本最低的兜底方案，但目标用户正是被终端劝退的人群，仅适合作为面向开发者的补充入口 |

### 5.3 推荐

- **默认推荐：Tauri 2 + React/TypeScript**。理由：满足"轻量 + 跨平台 + 本地系统操作"三项硬约束；CC Switch 用同一技术栈，如未来需要读取其数据库结构（`~/.cc-switch/cc-switch.db`）或参考其环境检测实现，可直接对照其开源代码（MIT 协议）；帮助文档模块用 Web 技术渲染 Markdown 也最自然。
- **若问题 #6 的答案是"实质上仅 Windows"**：改用 **WPF/WinUI 3**，放弃跨平台换取企业分发（MSI、静默安装、组策略）与团队维护成本上的优势。
- **不推荐 Electron**，除非团队完全没有 Rust/Go/C# 储备且交付时间极紧。

### 5.4 配套技术决策点

- 帮助文档格式：Markdown 内嵌 + 构建期打包；若走在线拉取（问题 #18），预留内部 Wiki API 对接层
- 遥测（若批准）：本地埋点 + 内网上报端点，不引入第三方 SDK
- 自动更新：Tauri 自带 updater 插件，但更新源需放内网（问题 #11/#13）
- 配置下发：公司标准参数（网关地址、模型名）建议做成随包 JSON 或内网配置端点，避免硬编码后每次变更都要发版

| 阶段 | 内容 | 出口标准 | 预估 |

## 七、主要风险与对策

| 风险 | 说明 | 对策 |
|------|------|------|
| 上游迭代 | 指南自述"软件迭代较快，以应用内实际显示为准"；CC Switch 界面与 Codex 配置格式都可能变化 | 定位上尽量少依赖 CC Switch 界面细节（倾向定位 B/C）；对 Codex 配置格式做版本探测，写入前校验；建立"上游发版 → 回归检查"的例行流程 |
| 配置文件所有权冲突 | 定位 B/C 下，本工具与 CC Switch（若用户自装）都写 `~/.codex/config.toml` | 写入前检测既有配置并备份；在配置文件中留注释标记来源；文档明确二者关系 |
| 权限与安全策略 | 自动安装可能被终端安全软件拦截，未签名产物触发系统告警 | 提前与 IT 确认签名证书与白名单流程（问题 #7/#12），将其列为 P0 阻塞项 |
| 密钥经手 | 连通性测试、诊断报告都可能触碰 API Key | Key 仅驻留内存，诊断报告强制脱敏，遥测不包含 Key 相关字段；方案送安全团队评审 |
| 做成"第二个 CC Switch" | 范围蔓延，重复造轮子 | 每个功能提案回答一个问题：CC Switch 是否已提供？若是，我们做的是编排还是替代？ |

## 附：与 IT 首次对齐会建议议程（60 分钟）
